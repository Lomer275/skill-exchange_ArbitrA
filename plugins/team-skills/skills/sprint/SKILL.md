# Sprint Skill

Автономный оркестратор выполнения спецификации. Читает все 🟡 задачи из спеки,
группирует в волны по зависимостям, выполняет каждую волну параллельно.

---

## Входные данные

- `/sprint S02` — выполнить все 🟡 задачи спецификации S02
- `/sprint S02 --dry-run` — только показать план волн, ничего не выполнять

Если номер спеки не передан — сообщить об ошибке и остановиться:
```
❌ Укажи номер спецификации: /sprint S02
```

## Алгоритм: Фаза 0 — Парсинг спеки и построение волн

### 0.1 — Найти файл спеки

Выполнить поиск:
```
glob docs/specifications/SNN_*.md
```
Если файл не найден — проверить `docs/backlog/` и `docs/specifications/*_done.md`.
Если всё равно не найден → СТОП:
```
❌ Спецификация S02 не найдена в docs/specifications/
```

### 0.2 — Собрать задачи со статусом 🟡

Прочитать файл спеки. Найти все строки таблицы задач где статус = 🟡.
Извлечь для каждой: номер TNN, название, колонку "Зависит от" (если есть).

Если 🟡 задач нет:
```
ℹ️ В спецификации S02 нет активных задач (все ✅ или 🔵).
```
Остановиться.

### 0.3 — Построить граф зависимостей

**Если в спеке есть явная колонка "Зависит от":**
- Строить граф по ней: TNN → [список TNN-блокеров]

**Fallback — если колонки нет:**
- Считать все задачи независимыми → одна волна, выполнять последовательно
  (параллелизм не применяется без явных зависимостей)

### 0.4 — Разбить на волны

Волна 1: задачи без блокеров (in-degree == 0)
Волна N: задачи, все блокеры которых выполнены в предыдущих волнах

Если граф содержит цикл → СТОП:
```
❌ Обнаружен цикл зависимостей: T05 → T06 → T05
Исправь таблицу зависимостей в спеке и запусти /sprint заново.
```

## Алгоритм: Фаза 1 — Предполётный план

После построения волн — вывести план до старта любого выполнения.

### 1.1 — Предварительное сканирование рисков

Для каждой задачи прочитать файл задачи и критерии приёмки.
Определить ожидаемые точки остановки (см. раздел "Определение рисков").

### 1.2 — Вывести план

```
## Sprint S02 — План

Волна 1: T05 ∥ T07
Волна 2: T06 ∥ T08

Ожидаемые точки остановки для тебя:
  ⚠️  T05 — рискованное изменение (миграция БД)
  🚀  T07 — деплой
  🧪  T06 — ручное тестирование (если авто-тесты не пройдут)

Итого: ~N точек где нужен ты. Продолжать? (да/нет)
```

Если точек остановки 0:
```
Ожидаемые точки остановки: нет (полностью автономно)
```

### 1.3 — Если --dry-run

Вывести план (шаг 1.2) и завершить. Ничего не выполнять. Подтверждения не запрашивать.

### 1.4 — Ждать подтверждения *(только без --dry-run)*

Ждать "да" / "ок" / "go" от пользователя.
При "нет" / "стоп" — завершить без выполнения.

## Алгоритм: Фаза 2 — Выполнение волн

### 2.1 — Для каждой волны

Объявить старт волны:
```
## Волна N/M — старт [T05, T07]
```

Если волна содержит более одной задачи — запустить параллельно через
`superpowers:dispatching-parallel-agents`. Каждый агент получает:
- Номер задачи TNN
- Путь к файлу задачи
- Инструкцию выполнить алгоритм "Выполнение одной задачи" ниже

Если волна содержит одну задачу — выполнить напрямую (без диспатча агента).

### 2.2 — Ждать завершения всех задач волны

Следующая волна стартует только после того, как ВСЕ задачи текущей волны
завершены (статус: ✅ done или ⚠️ blocked).

### 2.3 — Обработка заблокированных задач

Если задача завершилась со статусом ⚠️ blocked:
- Все задачи следующих волн, зависящие от неё, получают статус ⛔ skipped
- Независимые задачи следующих волн продолжают выполнение

### 2.4 — После всех волн

Вывести финальный отчёт (см. раздел "Финальный отчёт").

## Алгоритм: Выполнение одной задачи

Каждая задача TNN выполняется по следующему алгоритму.

---

### Шаг 1 — Сбор контекста *(параллельно)*

Параллельно прочитать:
- Файл задачи: `docs/tasks/TNN_*.md`
- Файл спеки (уже прочитан в Фазе 0 — переиспользовать)
- Все файлы кода упомянутые в задаче (секции "Затронутые файлы", "Files:")
- Связанные файлы (импорты, конфиги) если упомянуты

Извлечь из задачи:
- Критерии приёмки (Acceptance Criteria)
- Список изменяемых файлов
- Описание задачи

---

### Шаг 2 — Авто-валидация плана

Сгенерировать внутренний план имплементации (не показывать пользователю).

Проверить план против критериев приёмки:
- Для каждого критерия — есть ли в плане шаг который его выполняет?
- Если какой-то критерий не покрыт → СТОП:

```
⛔ T05 — план не покрывает критерии приёмки

Не покрыто:
  - AC#3: уведомление отправляется при изменении статуса сделки

Задача остановлена. Проверь описание задачи или скорректируй подход вручную.
```
Статус задачи → ⚠️ blocked. Не продолжать.

Если план покрывает все критерии → продолжить к шагу 3.

---

### Шаг 3 — Checkpoint *(только при RISKY или DEPLOY)*

Определить риски по правилам из раздела "Определение рисков".

**Если обнаружен DEPLOY или RISKY:**

Вывести план с пометками:
```
## T05 — Checkpoint перед выполнением

План:
  1. Добавить поле `status_changed_at` в модель Deal (RISKY: миграция БД)
  2. Обновить serializer
  3. Добавить сигнал post_save

⚠️ Требует твоего ок: миграция БД изменит схему таблицы deals.

Продолжать? (да/нет/пропустить задачу)
```

Ждать ответа:
- "да" / "ок" / "go" → продолжить
- "нет" / "стоп" → статус ⚠️ blocked
- "пропустить" → статус ⛔ skipped

**Если RISKY и DEPLOY отсутствуют** — шаг пропускается, выполнение сразу.

---

### Шаг 4 — Имплементация

Написать код согласно плану. Автономно, без остановок.

Если в процессе обнаружен **незапланированный риск** (паттерн из "Определение рисков"
который не был в плане шага 2) → НЕМЕДЛЕННЫЙ СТОП:

```
⛔ T05 — незапланированный риск в процессе имплементации

Обнаружено: изменение требует правки docker-compose.yml (DEPLOY)
Это не было в плане. Продолжать? (да/нет/пропустить задачу)
```

Ждать ответа пользователя перед продолжением.

---

### Шаг 5 — Тестирование

#### Авто-тесты

Запустить тесты затронутых модулей:
```bash
docker compose exec web python manage.py test Handler Tracker --verbosity=2
```
(или другую команду если указана в задаче)

**Если тесты прошли** → перейти к шагу 6.

**Если тесты упали:**
- Попытка 1: проанализировать traceback, найти причину, починить
- Попытка 2: после фикса запустить тесты снова
- Попытка 3: финальная попытка

После 3 провалов → СТОП, передать пользователю:
```
⛔ T05 — авто-тесты не прошли за 3 попытки

Последняя ошибка:
  AssertionError: Expected status 200, got 500
  File: Handler/tests.py:142

Что пробовал:
  1. Исправил импорт модели — не помогло
  2. Добавил migrate — не помогло
  3. Проверил fixtures — проблема в другом

Нужна твоя помощь. Опиши что сделать, или проверь тесты вручную.
```
Ждать инструкций. После получения инструкций — продолжить или завершить с ⚠️ blocked.

#### Ручное тестирование (MANUAL_TEST)

Если задача помечена MANUAL_TEST (UI-изменения без авто-тестов):
1. Сформулировать сценарий для проверки
2. Попробовать проверить самостоятельно (логи, API-ответы, статус сервисов)
3. Если самостоятельная проверка невозможна → запросить пользователя:

```
🧪 T05 — нужна ручная проверка

Что проверить:
  1. Открой бота и нажми "Мои документы"
  2. Убедись что появляется список с датами загрузки
  3. Нажми на документ — должно открыться превью

Жду подтверждения (ок/не работает + описание).
```

---

### Шаг 6 — Review loop

Выполнить скилл `review-loop` для текущей задачи.
Цикл `codereview → fix` до `CRITICAL==0 AND HIGH==0`, максимум 5 итераций.
Фиксы применяются в быстром режиме (без ожидания подтверждения).

---

### Шаг 7 — Accept + Push

После чистого review-loop:

1. Выполнить `/accept TNN` — скилл закроет задачу, перенесёт файл, обновит HANDOFF и CHANGELOG
2. Выполнить `/safe-push` — скилл проверит секреты, сформирует коммит, запушит

Объявить завершение:
```
✅ T05 — выполнено и закрыто
```

## Определение рисков

Сканировать файлы которые планируется изменить. Риск определяется по паттернам:

| Тип | Паттерны |
|-----|----------|
| `DEPLOY` | `docker-compose.yml`, `nginx.conf`, `.github/workflows/`, `Dockerfile`, `gunicorn` конфиги |
| `RISKY` | файлы с `migration`, `migrate`, `auth`, `password`, `token`, `SECRET`, env-переменные, внешние API (Bitrix, payment-providers, Supabase) |
| `MANUAL_TEST` | изменения в `tg_bot/keyboards`, `tg_bot/texts`, шаблоны сообщений, UI-handlers без unit-тестов |

**Незапланированный риск** — паттерн обнаружен в процессе имплементации (шаг 4), которого не было в плане шага 2.

## Финальный отчёт

После завершения всех волн вывести:

```
## Sprint S02 — Итог

| Задача | Статус     | Точки остановки        | Комментарий                   |
|--------|------------|------------------------|-------------------------------|
| T05    | ✅ done    | 1 (RISKY — ок)         | —                             |
| T07    | ✅ done    | 2 (DEPLOY, MANUAL_TEST)| ручное тестирование пройдено  |
| T06    | ✅ done    | 0                      | —                             |
| T08    | ⚠️ blocked | —                      | авто-тесты упали, ждёт тебя   |

Волн: 2 | Задач выполнено: 3/4 | Точек остановки: 3

Требуют внимания:
  ⚠️ T08 — опиши что делать или запусти /sprint S02 после исправления
```

## Правила

- **DEPLOY — всегда checkpoint**: деплой-изменения требуют подтверждения пользователя без исключений
- **RISKY — всегда checkpoint**: рискованные изменения требуют подтверждения
- **3 попытки на тесты**: если за 3 попытки тесты не прошли → эскалация к пользователю
- **Незапланированный риск → немедленный СТОП**: обнаружен в процессе имплементации → остановиться
- **Заблокированная задача не блокирует волну**: другие задачи той же волны продолжают
- **Зависимые от blocked → автоматически skipped**: не пытаться выполнять
- **Цикл зависимостей → СТОП на старте**: не пытаться разрулить автоматически
- **--dry-run → только план**: никаких изменений в коде, никакого accept/push
- **Fallback без зависимостей → последовательно**: безопасный дефолт когда граф не определён
- **safe-push после каждого accept**: не накапливать коммиты между задачами
